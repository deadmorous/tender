# 000094 M0 brief — certification harness, increment breakdown

The per-milestone brief for M0 (vibe 000093), incorporating the 2026-08-03
layout refinement: directory-per-challenge, six-digit global numbering, no
tier letter in names, fixed `test.py`, free-form `meta/`.

## Design decisions (small ones, settled here)

**Metadata + levels live in `test.py`, read by pytest itself.** Each
challenge declares itself at module level and marks its tests with the level
they certify:

```python
# challenges/000001_bac-cab-identity/test.py
from challenges import harness

CHALLENGE = harness.declare(
    title="bac-cab: a×(b×c) = b(a·c) − c(a·b)",
    tier="A",
    source="Lurie, Theory of Elasticity, appendix (tensor calculus)",
)

@harness.level("L1")
def test_verified():      # endpoint confirmed by component check
    ...

@harness.level("L2")
def test_performed():     # direct-notation derivation, public surface only
    ...
```

- A challenge's certified level = the highest level whose tests all pass.
- A not-yet-reachable level is a **strict xfail** (`@harness.level("L2",
  expected=False)`), so the red is enumerated, never skipped, and an
  unexpected pass flips CI red until the marker is removed — promotions are
  always explicit commits.
- `challenges/harness.py` is the single home for `declare`/`level` plus the
  shared assertion helpers challenges keep reusing (`assert_algebraic_eq`,
  chart-expansion component check). Nothing else goes in it — it is a test
  utility, not a product surface.

**Scoreboard is a committed, generated file** — `challenges/SCOREBOARD.md`,
grouped by tier from metadata, one row per challenge (number, title, level:
L0 failing / L1 verified / L2 performed). Generated by
`challenges/make_scoreboard.py` (runs pytest programmatically, renders the
table); a CI job regenerates and fails on diff, exactly the
`notebooks-clean` pattern. Committed rather than CI-only so the scoreboard
has history: `git log challenges/SCOREBOARD.md` *is* the product-progress
record.

**pytest config**: `--import-mode=importlib` (same-named `test.py` modules)
and challenge discovery rooted at `challenges/`, set in the repo-root pytest
configuration next to whatever the existing Python tests already use — one
config, both suites runnable separately (`pytest python/tests`,
`pytest challenges`).

**Numbering**: next number = max existing + 1, no central registry file.

## Increments

Each keeps the build and all existing tests green.

1. **Skeleton + first challenge.** `challenges/harness.py`, pytest config,
   and challenge `000001` (bac-cab via the existing eps-delta machinery,
   seeded from `examples/cross_identity.py` / `eps_delta.py`) passing at its
   honest level. *Done when:* `pytest challenges` collects and is green with
   exactly one challenge.
2. **Scoreboard.** `make_scoreboard.py` + committed `SCOREBOARD.md` +
   freshness check wired into CI alongside the existing jobs. *Done when:*
   editing a challenge without regenerating the scoreboard fails CI; the
   table groups by tier.
3. **Seed the already-proven material.** One challenge directory per
   existing proven endpoint, `test.py` distilled from the example (examples
   stay untouched, per CLAUDE.md they are never deleted): delta/eps
   identities (tier A), basis dot/round-trip material (B), curvilinear
   operator endpoints ∇R = I, Δr² cyl/sph, rot(r e_θ) (D), Navier–Lamé,
   strain compatibility, elastic-energy reduction (E). Where a hand
   derivation or notebook exists, its artifacts land in `meta/`. *Done
   when:* every seeded challenge is green at L1 or better, and the L2 tests
   exist as strict xfails wherever the current surface can't do L2 — that
   gap is the metric, it must be visible from day one.
4. **Enumerate the rest of vibe 000092 §4.** Challenge directories for every
   remaining A1–E4 item, each with metadata, a docstring stating the claim
   and source, and strict-xfail tests (L1 and L2). *Done when:* the
   scoreboard shows the complete A–E roster with its true red/green state.
5. **CI job.** `challenges` job running increments 1–4's suite +
   scoreboard-freshness on every push, alongside the existing build/test
   jobs. *Done when:* CI is green on the seeded state and a deliberately
   broken challenge turns it red.

Exit = vibe 000093 M0 exit criterion, now measurable: scoreboard exists,
CI-run, full tier list enumerated, expected-fail (never skip) for the
unreached parts.

## Out of scope for M0

No product-code changes at all — no new steps, no API adjustments, even
where a seed challenge would reach L2 with a small product fix. Such
findings become notes in the challenge's `meta/` and wait for M1–M4; M0 only
measures.
